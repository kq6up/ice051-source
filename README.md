# ICE 0.51 — recovered source

GitHub baseline: [contents, macOS run instructions, and reverting changes](docs/BASELINE.md).
The working Mac executable is preserved under `snapshots/macos-arm64/ice`; run it from `data/`.


Fortran source for the U.S. Naval Observatory's **Interactive Computer
Ephemeris, version 0.51** (Nautical Almanac Office, 1988–89), recovered from
`ICE.EXE` (Microsoft FORTRAN 4.x, DOS, EXEPACK-compressed, 8087 emulator).

No original source was available. Everything here was rebuilt from the
machine code. The program's logic, constants, order of evaluation, I/O
statements and FORMATs follow the binary routine by routine. Each routine's
header gives its address in the executable, e.g. `RISSET [0A09:0000]`. The
names of routines and variables are mine.

All 74 routines of the program are recovered, which is everything in the
executable except the Microsoft FORTRAN run-time library. That covers the
menu, all ten function keys, the NOVAS astrometry, the Chebyshev ephemeris
reader, the physical ephemeris, the catalogs and the five assembler helpers.

The `.for` files in `src/` are UTF-8, so the box-drawing characters can be
read and edited. The build converts them to code page 437, which is what the
program writes.

## Building and running (Linux, gfortran)

```sh
./build.sh                                  # -> build/ice
python3 setup_data.py /path/to/ice data     # convert PARAM.DAT, EPHnn.DAT; copy the rest
cd data && ../build/ice
```

The keys are F1–F10 as on the PC, and Alt-F1 redraws the menu. On a UTF-8
terminal the code page 437 screen is converted for display (set `ICE_CP437=1`
to turn this off). Files the program writes stay in code page 437, as the
original wrote them.

`./build.sh --deltat2026` builds the program with the 2026 ΔT table and with
the decimal year in F7 Navigation corrected to IY + IM/12 + ID/365.25 (the
original divides the day by 30). This build matches the patched
`ICE_DT26.EXE` screen for screen.

`PARAM.DAT` and `EPHnn.DAT` are Microsoft unformatted sequential files, so
`setup_data.py` re-frames them for gfortran. The catalogs are direct-access
files and are used as they are.

The `dos/` copies are written for Microsoft FORTRAN 4.x, large model, with
MASM for `SCRIO.ASM`. They have **not** been compiled with that compiler here.
Expect to adjust details: for example, `FORM='BINARY'` and the `$` edit
descriptor are MS extensions the source keeps.

## How it was checked

* **Routine level:** 35 routines were called inside the original
  executable (under a CPU emulator) and in the recovered source with the same
  random arguments: 60–400 cases each, including stateful sequences for the
  ephemeris reader. Character and integer routines, the coefficient unpacking,
  the ephemeris reader and the date routines agree exactly. Floating-point
  results agree to 1e-16–1e-11 relative. The few larger differences
  (nutation 1e-7, which is single precision in the original; refraction;
  sidereal time near 1e9 s) come from x87 register use, explained below.
* **Program level** (`verify/`): 86 scripted sessions covering every
  function key, error paths, both catalogs and file output. Each one is run
  through the original `ICE.EXE` (unpacked, under a small DOS emulator) and
  through the gfortran build. The final 80×25 screen, the complete stream of
  screen output and every file written are compared. All 86 agree, except
  for two known run-time differences, which are listed below: the last digit
  of some Chebyshev coefficients, and a file opened on two units.

```sh
pip install unicorn capstone numpy
verify/run.sh /path/to/ice            # all 86 sessions
verify/run.sh /path/to/ice F6         # only those whose name contains "F6"
```

`verify/prepare.py` unpacks `ICE.EXE` and checks it against the version used
here (ICE 0.51, 152 KB EXE).

## Known differences (run-time library, not the source)

* MS FORTRAN never prints the optional leading zero in F, E and D output
  (`  .7174172`, ` -.0474`), and gfortran always does (`0.7174172`). The
  comparison maps both to the MS form.
* MS FORTRAN keeps intermediate results in 80-bit registers across
  statements, while gfortran `-O0` stores them as doubles. This changes the
  last digit of a few of the 15-digit Chebyshev coefficients in the F3/F5
  listing (Moon, Mars, Jupiter; the Sun's are identical). Elsewhere the
  effect stays far below anything displayed.
* The MS run-time refuses to open a file that is already open on another
  unit, and gfortran allows it. This shows only if `ICE.DFT`, which the
  original never closes, is given to F9 as a catalog.
* `scrio.c` reproduces the console behaviour of the MS run-time, which
  gfortran lacks: carriage control, `PAUSE`, and a READ ending the pending
  output line.

The verification also turned up an emulator problem: QEMU/Unicorn computes
the x87 transcendental instructions in double precision, so the original
under emulation printed `10**3` as 1000.0000000000013. `verify/x87fix.py`
restores 80-bit results, which were checked against a real x87.

## Quirks of the original, kept as they are

* F7 Navigation forms the year as IY + IM/12 + **ID/30**, so ΔT is taken up
  to two years late in December. `--deltat2026` corrects this.
* If `ICE.DFT` is missing, the "built-in defaults" are replaced by zeros
  (`MENU`).
* `SOLSYS` can refresh the Sun and Moon from a stale buffer when the body's
  interval is still valid.
* F3/F5 writes the Chebyshev listing to unit 11, which is the catalog unit,
  and then closes it. If a catalog file is open, the listing goes into it.
* F6 tests `NUM .EQ. 0` where the Sun (10) was surely meant. As a result,
  evening twilight stays blank on days the Sun does not rise.
* F6 has `ANGSTR` write 10 characters into `CHARACTER*6 STRT(2)`, which
  relies on the two elements being adjacent. The astrometric-places file
  header is in column 28, while the screen header is in column 26.
* `LATLON` normalises the longitude in place, which changes `ALONG` in
  `/SITE/`. `CLRWIN` returns with `RET 8` for 16 bytes of arguments, but it
  is never called.
